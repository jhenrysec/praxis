## Intel Brief — Complete YAML Schema

This is the authoritative schema for all intel brief files stored in `intel_briefs/`.
Every field is documented. Required fields are marked. Optional fields should be
included when source material supports them.

```yaml

  schema_version: "1.0"
  generated_by: INTEL_AGENT
  generated_date: "YYYY-MM-DD"                    # required
  fidelity: balanced                               # required: strict|balanced|loose

  source:
    type: ""        # required: mitre_attack | cisa_advisory | ics_cert |
                    #           ir_report | whitepaper | operator_provided | other
    title: ""       # required
    url: ""         # required if web source, "operator-provided" otherwise
    date: ""        # publication date if available
    authors: []     # optional
    tlp: WHITE      # TLP classification of source: WHITE|GREEN|AMBER|RED
    operator_notes: ""  # optional: anything the operator flagged at ingestion time

  adversary:
    name: ""        # required if attributable
    aliases: []
    motivation: ""  # espionage | financial | destructive | hacktivism | unknown
    target_sectors: []
    known_tools: []
    sophistication: ""  # nation_state | organized_crime | hacktivist | unknown

# ── LAYER 1: ATTACK SCHEME OF MANEUVER ───────────────────────────────────────
attack_scheme:
  summary: ""       # required: 2-4 sentence narrative of the full attack chain

  phases:           # required: ordered list, at least one entry
    - order: 1      # required: integer, sequential
      phase: ""     # required: ATT&CK tactic name
      tactic_id: "" # required: ATT&CK tactic ID (TA####)

      technique: "" # required: ATT&CK technique ID (T#### or T####.###)
      technique_name: ""  # required
      sub_technique: ""   # optional: sub-technique ID if applicable
      ics_technique: false  # true if this is ATT&CK for ICS (not Enterprise)

      adversary_action: ""   # required: what they did, in source's own terms
      why_it_worked: ""      # required: environmental condition that enabled it
      source_quote: ""       # optional: direct quote from source if available

      lab_objective: ""      # required: what student must do to replicate/detect
      detection_opportunity: ""  # required: what defender sees if monitoring
      detection_artifacts: []    # optional: specific log sources, event IDs

      fidelity_note: ""      # optional: how lab implementation differs from source
      instructor_only: false # true if this is background context, not student-visible

    # Things the adversary specifically relied on — must be present in lab
    required_conditions: []

# ── LAYER 2: TOPOLOGY CONTEXT ─────────────────────────────────────────────────

  available_in_source: true   # false if source had no topology detail

                    #           defense_dib|transportation|government|other
  subsector: ""     # optional: electric_utility|oil_gas|wastewater|etc.

  environment_description: ""   # required: 2-4 sentence narrative

  critical_topology_facts: []   # required: bullet list of structural conditions

  what_made_it_vulnerable:      # required: list of condition→enables pairs
    - condition: ""
      enables: ""
      lab_implementation: ""    # specific bridge/rule/config in Jason's lab

  lab_zone_mapping:             # how source zones map to lab bridges
    - source_zone: ""
      lab_bridge: ""            # vmbr0|vmbr1|vmbr2|vmbr3
      ip_range: ""
      notes: ""

  topology_requirements:        # required: specific configs INFRA_AGENT must implement
    - requirement: ""
      implements_as:
        type: ""                # pfSense_rule|vm_dual_home|vlan|bridge_config
        detail: ""              # specific config (e.g., "PERMIT TCP/502 from 10.10.2.30")
      rationale: ""
      is_misconfiguration: false  # true=bug, false=legitimate business need abused

# ── LAYER 3: INFRASTRUCTURE INVENTORY ────────────────────────────────────────
infrastructure:
  available_in_source: true

  assets:                       # required: list of all relevant assets
    - role: ""                  # required: boundary_appliance|workstation|server|
                                #           plc|hmi|historian|domain_controller|
                                #           firewall|switch|other
      zone: ""                  # where it sat in the source network

      # Source details
      source_product: ""        # exact product name from source
      source_vendor: ""
      source_version: ""        # exact version string from source
      source_patch_state: ""    # patched|unpatched|unknown + details
      source_cve: ""            # CVE ID if specific vuln was exploited
      source_cve_description: ""
      source_notes: ""          # anything else the source says about this asset

      # Lab substitution
      substitution:
        needed: true            # false if exact template match exists
        template: ""            # lab template name: tpl-kali-2024, tpl-win10-workstation, etc.
        service: ""             # specific service/software on the template
        version: ""             # version deployed in lab
        ansible_role: ""        # role that configures the substitution
        technique_preserved: true   # required: does substitution preserve ATT&CK technique
        fidelity_loss: ""           # what training value is lost, if any
        fidelity_note: ""           # explanation for scenario card
        licensing_constraint: false # true if original product not usable due to license

      # VM configuration derived from source context
      vm_config:
        cpu_cores: 2
        memory_mb: 2048
        disk_gb: 40

        additional_config: []   # extra Ansible tasks needed

      type: ""                  # windows_event|network_pcap|filesystem_artifact|
                                # registry_key|log_entry|scheduled_task|
                                # prefetch|memory_artifact|network_connection
      host_role: ""             # which VM role this artifact lives on
      description: ""           # required: what this artifact represents
      source_detail: ""         # exact detail from source (event ID, file path, etc.)

      # Staging configuration
      staging:
        method: ""              # ansible_task|pre_captured_pcap|script|file_drop
        ansible_role: ""        # role name if ansible_task
        file_path: ""           # destination path on VM
        file_source: ""         # path in repo: artifacts/<scenario>/
        pre_scenario: true      # true = staged before student access

      # Training value
      detection_value: ""       # what skill this artifact teaches when found
      intentional: true         # true = adversary knowingly left it
                                # false = inadvertent (tests adversary opsec understanding)
      difficulty: ""            # easy|medium|hard — how hard to find in the lab
      hint_available: false     # instructor can send hint pointing to this artifact

  # Raw IOC data from source (for reference, not necessarily all stageable)
  raw_iocs:
    ip_addresses: []
    domains: []
    file_hashes: []
    file_names: []
    registry_keys: []
    mutex_names: []
    user_agents: []

operational_context:
  sector: ""          # required: matches topology_context.sector
  subsector: ""
  org_type: ""        # e.g., "Regional electric utility", "Tier 2 manufacturer"

  environment_narrative: ""     # required: 3-5 sentences describing the org
                                # written for the student scenario brief

  regulatory_context: []        # relevant regulations/frameworks:
                                # NERC CIP, AWIA, CMMC, HIPAA, TSA Pipeline, etc.

  scenario_brief_for_students: ""   # required: what students are told before starting
                                    # written in second person, establishes role/mission

      host_role: ""             # which VM role receives this asset
      type: ""                  # document|spreadsheet|email|log|process_data|
                                # ad_structure|sop|config_file|diagram|database
      filename: ""              # exact filename to use on the VM
      file_path: ""             # full path on VM: C:\Users\...\Desktop\filename
      format: ""                # docx|xlsx|pdf|txt|csv|json|xml|vsdx|etc.

      content_brief: ""         # required: detailed description of file contents
                                # specific enough for content generation to produce
                                # a realistic, sector-accurate artifact

      sector_references: []     # specific terminology, standards, or systems
                                # that should appear in the document

      training_purpose: ""      # clue|red_herring|reward|baseline|context|lore

      generates_via: ""         # docx_skill|xlsx_skill|pdf_skill|script|manual
                                # references the appropriate generation skill

      ansible_task: ""          # ansible task that drops this file on the VM

    netbios: ""
    ous: []

        title: ""
        department: ""
        description: ""
        spn: ""                 # set if Kerberoastable
        password_policy: ""     # weak|standard|strong

## Source Type Handling Patterns

### MITRE ATT&CK Technique Page

```
URL pattern: https://attack.mitre.org/techniques/T####/
             https://attack.mitre.org/techniques/T####/###/  (sub-technique)

Fetch strategy:
  1. Main technique page → Layer 1 (description, platforms, permissions required)
  2. "Procedure Examples" section → Layer 1 detail (real-world adversary usage)
  3. "Mitigations" section → Layer 4 (detection artifacts)
  4. "Detection" section → Layer 4 (detection opportunities)

Layer availability:
  Layer 1: HIGH — core content
  Layer 2: LOW — technique pages rarely describe topology
  Layer 3: MEDIUM — platforms and requirements give infrastructure hints
  Layer 4: HIGH — detection section
  Layer 5: LOW — no organizational context

Note: For richer briefs from ATT&CK, also fetch the Group page
(https://attack.mitre.org/groups/G####/) and any associated Campaign pages.
Group pages provide Layers 2 and 3 context that technique pages lack.
```

### CISA Advisory

```
URL patterns: https://www.cisa.gov/news-events/cybersecurity-advisories/aa##-###
              https://www.cisa.gov/uscert/ics/advisories/icsa-##-###-##

Fetch strategy:
  1. Main advisory page → all layers
  2. Any linked technical appendices → Layer 3 and 4 detail
  3. Any linked STIX/JSON IOC files → Layer 4 raw IOCs
  4. Any associated MITRE ATT&CK Navigator layers → Layer 1 validation

Layer availability:
  Layer 1: HIGH
  Layer 2: MEDIUM — CISA advisories often include network diagrams or
                     descriptions of victim topology
  Layer 3: HIGH — advisories typically list affected products and versions
  Layer 4: HIGH — IOC tables are a CISA standard
  Layer 5: MEDIUM — sector is always clear, specific org details vary

ICS-CERT specific notes:
  - Always check for associated Modbus/DNP3/EtherNet-IP register details
  - Affected product versions are usually exact — use them directly in Layer 3
  - Often include vendor mitigations that reveal the attack surface clearly
```

### Incident Response / Threat Intelligence Report

```
Examples: Mandiant APT reports, CrowdStrike Adversary Intelligence,
          Dragos Year in Review, Claroty research, vendor IR reports

Fetch strategy:
  1. Executive summary → attack narrative for Layer 1 summary
  2. Technical analysis sections → all five layers
  3. Appendices (IOC tables, YARA rules, network diagrams) → Layer 3 and 4
  4. ATT&CK mapping tables (if included) → validate Layer 1

Layer availability:
  Layer 1: VERY HIGH — IR reports typically have detailed TTP chains
  Layer 2: HIGH — IR reports often describe victim environment in detail
  Layer 3: HIGH — specific products, versions, patch states
  Layer 4: VERY HIGH — IOC appendices are standard
  Layer 5: HIGH — victim sector and organization type usually described

Note: Some commercial reports are behind paywalls. If web_fetch fails,
ask operator to paste the relevant sections.
```

### Whitepaper / Research Paper

```
Variable structure — apply general extraction logic.

Prioritize:
  - Any section titled "Attack Chain", "Intrusion Timeline", "TTPs", "Methodology"
  - Network diagrams (describe topology → Layer 2)
  - "Affected Systems" or "Infrastructure" sections → Layer 3
  - "Indicators of Compromise" or "Detection" sections → Layer 4
  - "Background" or "Victim Profile" sections → Layer 5

If the paper is academic and does not describe a specific incident,
Layer 5 will be minimal. Layer 1 may describe techniques generically
rather than as observed adversary behavior — flag this distinction
in the brief metadata.
```

## Sector Dressing Reference

### Energy — Electric Utility
```
Regulatory: NERC CIP (CIP-002 through CIP-014)
Terminology: BES (Bulk Electric System), EMS (Energy Management System),
             SCADA, substation, relay, RTU, PMU, historian, DCS,
             ESP (Electronic Security Perimeter), EAP (Electronic Access Point)

Realistic dressing documents:
  - Substation maintenance SOP (references specific relay models, Modbus addresses)
  - Shift handover log (normal process readings → baseline for anomaly detection)
  - CIP-007 patch management log (shows what was patched and what wasn't)
  - Vendor remote access request form (establishes third-party access as normal)
  - Network diagram marked CONFIDENTIAL (reward for thorough enumeration)
  - Emergency response procedure (establishes what normal incident response looks like)

AD structure:
  OUs: Operations, Engineering, IT, SCADA_Systems, Contractors
  Service accounts: svc_historian, svc_scada_read, svc_ems_write
  SPNs: SCADA/historian.utility.local, EMS/ems-server.utility.local
```

### Energy — Oil and Gas / Pipeline
```
Regulatory: TSA Pipeline Security Directives, API 1164
Terminology: SCADA, RTU, compressor station, metering, injection point,
             emergency shutdown (ESD), safety instrumented system (SIS),
             historian, DCS, HMI

Realistic dressing documents:
  - Pipeline SCADA alarm management procedure
  - Compressor station startup SOP
  - Emergency shutdown test record
  - Leak detection system calibration log
  - API 1164 compliance checklist
```

### Water / Wastewater
```
Regulatory: AWIA (America's Water Infrastructure Act), EPA guidance
Terminology: SCADA, PLC, HMI, treatment process, chemical dosing,
             chlorination, turbidity, flow rate, pump station,
             lift station, CEMS

Realistic dressing documents:
  - Chemical dosing SOP (chlorine, coagulant — references specific setpoints)
  - Daily operations log (normal readings → anomaly baseline)
  - Pump station maintenance record
  - EPA compliance report
  - Emergency response plan (establishes incident notification chain)
```

### Manufacturing
```
Regulatory: ISA/IEC 62443, NIST SP 800-82
Terminology: MES (Manufacturing Execution System), DCS, PLC, HMI,
             production schedule, quality control, OEE,
             recipe management, batch record

Realistic dressing documents:
  - Production schedule (establishes what's being made → attack impact context)
  - Quality control record (normal process parameters)
  - MES batch record (process historian data)
  - Equipment maintenance log
  - ISO 9001 audit checklist
```

### Financial
```
Regulatory: PCI DSS, SOX, FINRA
Terminology: trading system, order management, clearing, settlement,
             core banking, SWIFT, transaction log, audit trail

Realistic dressing documents:
  - Transaction log excerpt (fake account numbers, realistic amounts)
  - Trading system configuration (connectivity to exchanges)
  - SOX compliance checklist
  - Incident response runbook
  - Fake financial spreadsheets (budget, P&L — realistic but obviously fake orgs)
```

### Healthcare
```
Regulatory: HIPAA, HITECH, FDA (medical devices)
Terminology: EHR, HL7, DICOM, medical device, infusion pump,
             patient monitoring, PACS, clinical workstation

Realistic dressing documents:
  - HL7 interface specification (technical, not patient data)
  - Medical device network diagram
  - HIPAA risk assessment
  - Biomedical equipment maintenance log
  - Clinical workflow SOP
```

### Defense / DIB
```
Regulatory: CMMC, DFARS, NIST SP 800-171
Terminology: CUI (Controlled Unclassified Information), ITAR,
             program office, contract, CDRLs, system security plan

Realistic dressing documents:
  - System security plan (sanitized, no real program details)
  - CMMC assessment checklist
  - CUI handling procedure
  - IT asset register (fake hostnames, realistic structure)
  - Incident response plan

## Ansible Integration Patterns

### Staging a Windows Event Log Artifact

```yaml
# roles/stage-windows-artifacts/tasks/main.yml
# Injects pre-built Windows event log entries for forensic scenarios

- name: "[STAGE] Copy event log injection script"
  ansible.windows.win_copy:
    src: "files/inject_events.ps1"
    dest: "C:\\Windows\\Temp\\inject_events.ps1"

- name: "[STAGE] Inject scenario event log artifacts"
  ansible.windows.win_shell: |
    # Inject Event ID 4698 - Scheduled task created
    $xml = Get-Content "C:\Windows\Temp\event_4698.xml"
    wevtutil im "C:\Windows\Temp\event_4698.xml"
  args:
    executable: powershell

- name: "[STAGE] Remove injection artifacts"
  ansible.windows.win_file:
    path: "C:\\Windows\\Temp\\inject_events.ps1"
    state: absent
```

### Staging a PCAP File

```yaml
# roles/stage-pcap-artifacts/tasks/main.yml

- name: "[STAGE] Create artifacts directory on analyst VM"
  ansible.builtin.file:
    path: /home/analyst/artifacts
    state: directory
    owner: analyst

- name: "[STAGE] Copy scenario PCAP"
  ansible.builtin.copy:
    src: "files/{{ scenario_name }}_modbus_recon.pcap"
    dest: "/home/analyst/artifacts/capture_2024-03-15.pcap"
    owner: analyst
    mode: '0644'
```

## Content Generation Integration

Dressing assets with `generates_via: docx_skill` or `generates_via: xlsx_skill`
are generated programmatically during scenario build. The content brief from
Layer 5 is passed as the generation prompt.

```
Generation trigger (after INTEL_AGENT brief is complete):

For each dressing_asset where generates_via != "manual":
  1. Read content_brief from brief YAML
  2. Load appropriate skill (docx_skill, xlsx_skill, pdf_skill)
  3. Generate file using content_brief as prompt
  4. Store generated file in: scenarios/<name>/ansible/roles/stage-dressing/files/
  5. Ansible role picks it up and drops it on the VM during deployment
```

The content brief must be specific enough for generation. Bad:
  "A maintenance document"
Good:
  "A 3-page NERC CIP-007 patch management log for Substation 42. Contains a table
   of 12 assets (SEL relay models, GE multilin, ABB RTU) with columns for asset name,
   current firmware version, last patched date, and next scheduled patch. The OpenPLC
   controller at 192.168.100.10 appears in the list as unpatched for 8 months.
   Uses realistic utility letterhead for 'Tri-County Electric Cooperative'."

That second version gives the content generator everything it needs to produce
a realistic, scenario-accurate document that contains the right technical detail
for students to find meaningful.

## Common Extraction Pitfalls

| Issue | How to handle |
|---|---|
| Source is vague about topology | Extract what exists, mark Layer 2 as partial, note INFRA_AGENT must use reasonable defaults for the sector |
| Version numbers not specified | Use "unknown" not a guess — INFRA_AGENT should deploy latest available |
| Source attributes to multiple adversaries | Extract the most specific attribution available, note ambiguity in metadata |
| Source describes technique but not specific tool | Extract technique, leave tool unspecified — let SCADA_AGENT/INFRA_AGENT choose appropriate lab tool |
| Source contradicts itself | Note both versions, flag for instructor review |
| PDF is image-based (scanned) | Use pdf-reading SKILL.md OCR approach, note reduced extraction confidence |
| Source requires login/paywall | Prompt operator for content paste, do not attempt bypass |
| ATT&CK technique ID has changed between versions | Use current v15 Enterprise or v2 ICS IDs, note if source used older ID |
