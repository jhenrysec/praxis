# Lesson Plan — SCADA Modbus Recon & Manipulation

## Course Information
- **Scenario**: SCEN-001
- **Duration**: 2 hours (15 min brief + 75 min lab + 30 min debrief)
- **Difficulty**: Beginner
- **Class Size**: Up to 20 students (solo)
- **Prerequisites**: TCP/IP networking basics, Linux command line, familiarity with SCADA concepts

## Learning Objectives

By the end of this lab, students will be able to:
1. Use nmap to discover ICS devices on an OT network segment (T0846)
2. Enumerate Modbus TCP coils and registers using pymodbus (T0842)
3. Map a PLC register table to understand process control logic
4. Write to Modbus holding registers and coils to manipulate process parameters (T0836, T0855)
5. Explain why Modbus TCP lacks authentication and describe defense-in-depth strategies for ICS environments

## Pre-Class Preparation

### Instructor Setup (30 min before class)
1. Deploy scenario: Portal Dashboard → Lab Slots → Select slot → Deploy `scada_modbus_recon`
2. Verify all VMs are running: check slot status shows "running" with 3 VMs
3. Open Grafana on the historian (`http://<historian_ip>:3000`, admin / LabGrafana2024!) and confirm the SCADA Process Monitor dashboard shows live tank level data
4. Distribute student access sheets (Kali IP, OT subnet, default creds)

### Student Prerequisites
- Comfortable with Python scripting (pymodbus is a Python library)
- Understand TCP/IP port scanning concepts
- Read the ICS/SCADA primer document (if unfamiliar with PLCs, HMIs, historians)

## Lesson Flow

### Phase 0: Briefing (15 min)

**Instructor presents:**
- What is SCADA? PLC? HMI? Historian? (2 min refresher, skip if class is experienced)
- Modbus protocol: designed 1979 for serial RS-485, later adapted to TCP/IP
- No authentication, no encryption — by design, not by misconfiguration
- Scenario setting: You are a red team operator who has gained network access to an OT segment. A water tank fill process is running on an OpenPLC controller.

**Discussion questions:**
- "Why might an attacker target an ICS environment?"
  - *Expected*: Physical impact, safety risk, leverage for ransom, nation-state pre-positioning
- "If Modbus has no authentication, what is the primary security control?"
  - *Expected*: Network segmentation — keep untrusted hosts off the OT network

### Phase 1: Reconnaissance (20 min)

**Technique**: T0846 — Remote System Discovery

**Student task**: From the Kali attacker, discover all hosts on the OT subnet and identify which services are running.

**Detection checkpoint**: "If a defender were monitoring, what would they see?"
- *Expected*: Nmap SYN scans to port 502 (Modbus), 8080, 8086, 3000. Unusual source IP issuing ARP requests on the OT VLAN.

**Hints (use portal hint system):**
1. Direction: "Start by scanning the OT subnet for live hosts"
2. Approach: "Use `nmap -sT -p 502,8080,8086,3000` against the OT subnet"
3. Near-answer: "The PLC is at .10 with port 502 open. The historian is at .20 with ports 8086 and 3000."

**Key teaching point**: In real ICS environments, active scanning can crash legacy PLCs. Passive discovery (traffic sniffing, ARP table inspection) is preferred for initial recon. We use active scanning here because OpenPLC handles it safely.

### Phase 2: Modbus Enumeration (25 min)

**Technique**: T0842 — Network Sniffing / Protocol Analysis

**Student task**: Use pymodbus to read all coils (FC01), input registers (FC04), and holding registers (FC03). Document a register map.

**Instructor walkthrough** (if students are stuck after 15 min):
1. Show the pymodbus import and connection pattern
2. Explain Modbus function codes: FC01 (read coils), FC03 (read holding registers), FC04 (read input registers)
3. Mention that OpenPLC maps %MW variables to holding registers starting at address 1024

**Detection checkpoint**: "What network traffic is generated by Modbus reads?"
- *Expected*: TCP connections to port 502, Modbus function code 01/03/04 requests. A Modbus-aware IDS (e.g., Suricata with ET ICS rules) would alert on reads from unknown source IPs.

**Hints:**
1. Direction: "Use the pymodbus library to connect and read different register types"
2. Approach: "Try `c.read_coils(0, 8)`, `c.read_input_registers(0, 4)`, and `c.read_holding_registers(1024, 3)`"
3. Near-answer: "Coil 0 is the pump enable. HR 1024 is the setpoint (750). HR 1025 is alarm high (900)."

**Key teaching point**: Modbus register enumeration is reconnaissance — the attacker learns the control logic without making any changes. This phase is analogous to AD enumeration in IT attacks.

### Phase 3: Process Manipulation (20 min)

**Techniques**: T0836 — Modify Parameter, T0855 — Unauthorized Command Message

**Student task**: Write an unsafe setpoint value (>900) to HR 1024 using FC06, then disable the pump by writing FALSE to coil 0 using FC05. Observe the impact on the Grafana dashboard.

**Instructor walkthrough:**
1. `c.write_register(1024, 999, slave=1)` — sets the target level to 99.9%
2. `c.write_coil(0, False, slave=1)` — disables the pump
3. Note: the PLC scan cycle overwrites coil 0 every ~50ms. Students may need to write continuously or observe that their write is immediately reverted — this is a teaching moment about PLC scan behavior.

**Detection checkpoint**: "What is different about FC05/FC06 traffic vs FC01/FC03?"
- *Expected*: FC05/FC06 are write operations. An IDS should treat Modbus writes from unknown IPs as HIGH severity alerts. Historian data would show sudden setpoint changes.

**Hints:**
1. Direction: "Use pymodbus write functions to change register values"
2. Approach: "Try `c.write_register(1024, 999)` and check the Grafana dashboard"
3. Near-answer: "Write to HR 1024 (setpoint), then write FALSE to coil 0 (pump disable). Open Grafana at `http://<historian_ip>:3000`"

**Key teaching point**: The Modbus write succeeds instantly with no challenge, no confirmation, no audit log on the PLC. This is not a vulnerability being exploited — this is the protocol working as designed.

### Phase 4: Advanced — Alarm Suppression (10 min, optional)

**Student task**: Before overfilling the tank, raise the alarm high threshold above the sensor range (HR 1025 → 1000). Then set the setpoint to 999. Observe that no alarm fires despite the overfill.

**Key teaching point**: This is why monitoring threshold changes is as important as monitoring process values. An attacker who modifies only the setpoint triggers alarms. An attacker who modifies the alarm thresholds first can attack silently.

### Phase 5: Debrief (30 min)

**Guided discussion:**

1. Walk through the full attack chain on the whiteboard: recon → enumerate → read → write → impact
2. Ask students: "At which phase could a defender have detected and stopped this?"
3. Real-world parallels:
   - **Oldsmar, FL (2021)**: Attacker accessed water treatment HMI via TeamViewer, changed NaOH dosing from 100ppm to 11,100ppm. Operator noticed the cursor moving and reverted the change.
   - **TRITON/TRISIS (2017)**: Attackers targeted Schneider Triconex safety controllers — the last line of defense against catastrophic failure.
4. "Why can't we just add TLS/authentication to Modbus?" — Many PLCs lack CPU power for crypto. Protocol migration is multi-decade in ICS. Defense must assume the protocol is insecure.
5. Defense discussion: Network segmentation, Modbus-aware IDS (Snort/Suricata), data diodes, monitoring setpoint changes in the historian

**ATT&CK mapping exercise**: Have students fill in the technique table from their notes before revealing the answer.

## Contingency Plans

### If students finish early
- Attempt the alarm suppression bonus objective
- Write Suricata IDS rules to detect Modbus writes from unauthorized sources
- Write an InfluxDB Flux query to detect anomalous setpoint changes
- Explore the OpenPLC web UI (port 8080, openplc/openplc) and examine the ladder logic program

### If students are stuck
- Use the portal hint system to push graduated hints to specific student slots
- After 10 minutes stuck on any phase, provide the next hint level
- For Phase 2 (pymodbus), show the connection boilerplate code on screen — students should figure out the register addresses themselves
- Never reveal the full solution — guide toward the next discovery step

### If infrastructure fails
- Admin Portal → Lab Slots → Reset to Baseline (resets VMs to pre-scenario snapshot)
- If reset fails: Destroy → Redeploy (~5 min)
- Fallback: Walk through the scenario as a live demonstration from the instructor console
- Have pre-captured screenshots of each phase in case of complete infrastructure failure
